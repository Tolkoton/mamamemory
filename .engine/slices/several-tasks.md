# Slice several-tasks — planning artifact

Режим: driven, `/feature-architect f2-week-planning`, slice S1 (TRACER BULLET). Рамка —
`.engine/architecture/feature/f2-week-planning.md` (S1, AC1, AC3a, AC6, AC7); спирається на запечатані S3
(`one-task-to-calendar.md`) і S4 (`open-questions.md`) F1. Поведінка однієї задачі S3 лишається незмінною
(запечатані тести S3 і S4 мають бути зелені без змін).

## Goal
Мама каже кілька задач одним повідомленням («у понеділок подзвонити нотаріусу на пів години, купити насіння, а в
середу о десятій до лікаря на годину») або кількома поспіль, поки план не записано. Система розбирає кожну задачу як
«на час» чи «без часу», бере названий день без часу («у понеділок»), питає тривалість по одному для задач на час без
тривалості, показує один план трьома групами (на час / без часу / не вмістилось). Одне «так» записує кожну задачу на
час подією без дублів. Мірило: тести зелені; tracer на розгорнутій адресі зі справжньою моделлю (критерій фічі).

## Premise verified
- Машина станів S3 (чернетка, відбиток, T0, «показано → записується → записано», крок 0 по `event_id`) — `verified`
  тестами S3 і S4.
- `event_id(plan_id, task_id)` дає різний id на задачу — `verified` (`google_work.py`).
- P-PARSE (Flash-Lite розбирає кілька задач з днем, тривалістю, «без часу») — `unverified`; у тестах підставна
  модель; перевіряє tracer на розгорнутій адресі (Exit criterion).

## Out of scope (deliberately)
- питання «що важливіше?» (S3 F2), межі часу мами (S2 F2), Google Tasks (S4 F2), правки голосом (S5 F2);
- задачі без часу й «не вмістилось» на «так» не пишуться нікуди (до S4 F2): мамі — рядок «Ці задачі запишу в Tasks
  пізніше.».

## Seam (contract)
- Чернетка (`plans/current`): `tasks: [Task]`, де `Task = {task_id: "t1".."tN", title, needs_time: bool,
  duration_min: int|null, start_local: str|null, constraints: {day: "YYYY-MM-DD"|null}, order: int, source: "speech",
  written: {event_id: str|null, tasks_id: null, closed: false}}`; решта полів як у S3 (`plan_id`, `state`,
  `horizon_end`, `t0`, `fingerprint`, `tz`, `writing_started`). Документ S3 з одним полем `task` читається як список з
  однієї задачі.
- `planning.start(...)` (той самий підпис S3): розбір моделлю `parse_tasks` → список `TaskDraft{title,
  needs_time, start_local, day, duration_min}`; якщо чернетка «питаю тривалість» чи «показано» і ще не записана —
  нові задачі додаються до неї (`order` продовжується), інакше — нова чернетка. Далі `next_question`.
- `planning.next_question(draft) -> Question | None` — чиста; слоти в порядку domain-map: «важливість» (у цьому
  slice завжди порожній), «тривалість» — перша задача з `needs_time` без `duration_min` → `Question("duration",
  plan_id, None)` з текстом «Скільки часу це займе?», коли така задача в чернетці одна (як S3), і «Скільки часу
  займе «<назва>»?», коли їх кілька; «межі» (порожній); `None` → показ плану.
- `planning.answer_duration(...)` (підпис S3) ставить тривалість задачі, про яку питали (перша без тривалості), і
  знову кличе `next_question`.
- `placement.place_many(tasks: list[TaskSpec], busy, *, now, tz, step_min, horizon_end, t0, limits=None) ->
  Placement{placed: list[(task_id, start, end)], unplaced: list[task_id]}` — чиста; спершу кожна задача з названим
  часом (`start_local`) — рівно як `place` S3 (без перевірки зайнятості, S3 Q2), і вона одразу стає зайнятістю;
  потім решта задач на час у порядку `order`, кожна поставлена стає зайнятістю для наступних; названий день
  (`constraints.day`) — найраніший вільний відрізок лише в цей день (у поясі `tz`); не вміщається — `unplaced`.
  На вході — лише ще не записані задачі на час; записані виходять зі списку, а їхні події — звичайна зайнятість
  календаря на справжній час (M2). `place` S3
  лишається й дає той самий результат для однієї задачі. `TaskSpec` дістає поле `day: date | None = None`.
- `PlanView` дістає поля `items: list[{task_id, title, start, end}]`, `untimed: list[{task_id, title}]`,
  `unplaced: list[{task_id, title}]` (за замовчуванням порожні); `title`, `start`, `end` — першої поставленої задачі
  (як у S3). Відбиток — хеш від `plan_id`, незаписаних задач (без поля `written`) і їхніх розставлених
  `(task_id, start, end)` та `unplaced`; часткове записування тому змінює відбиток.
- Текст показу: «Пропоную:» і рядок на кожну задачу на час («понеділок, 9 листопада, 10:15–10:45 — подзвонити
  нотаріусу»), потім «Без часу: …», «Не вмістилось: …», «Записати?».
- `confirm` (підпис S3): крок 0 — для кожної незаписаної задачі на час шукає її подію за `event_id(plan_id,
  task_id)` (у `list_events`, інакше `get_event`); знайдена — `written.event_id` записується; потім перерахунок
  решти й відбиток решти; той самий відбиток → «показано → записується» → по задачі: читання за id, створення,
  одразу запис `written.event_id` окремою транзакцією, що проходить лише за того самого `writing_started` → коли
  кожна поставлена задача має `written.event_id` — «записано». Обірваний запис → «показано»; наступне «так» зі
  старим відбитком бачить інший відбиток (решта) і показує решту як новий план з текстом «Записано не повністю —
  ось решта:» без жодного запису; порожня решта → одразу «записано». Відповідь — «Записала в календар.» і, якщо є
  задачі без часу чи «не вмістилось», рядок «Ці задачі запишу в Tasks пізніше.»; план лише з задачами без часу на
  «так» відповідає лише цим рядком (подій немає). Задача, додана до показаної чернетки, — новий показ з тими самими
  `horizon_end` і новим T0 (гілка 3 S3); до частково записаної решти — так само, записані лишаються записаними.
- `start` під час свіжого «записується» не чіпає чернетку й відповідає «Записую, хвилинку.»; повідомлення, з якого
  модель не дістала жодної задачі, не змінює чернетку й дістає «Не зрозуміла задачу, скажіть ще раз.».
- `open_question` S4 показує той самий план кількох задач.
- Does NOT do: Tasks, межі, пріоритети, правки.

## Decisions (with WHY)
- Q1: Нові задачі до незаписаної чернетки додаються, а не замінюють її. Чому: мама каже задачі кількома
  повідомленнями (AC1 «і з кількох поспіль»). Rejected: кожне повідомлення — новий план (як S3) — найсильніше за:
  простіше; але друге повідомлення губить першу задачу.
- Q2: `PlanView` розширюється полями, а не замінюється. Чому: запечатані тести S3/S4 читають `plan.start/end`;
  застосунок старих полів не втрачає. Rejected: новий тип — найсильніше за: чистіше; але ламає запечатаний контракт.
- Q3: Тривалість питається по одній задачі. Чому: domain-map — «короткі питання по одному»; мамі «дорого в фокусі».
  Rejected: одним питанням про всі — найсильніше за: менше кроків; але довга відповідь, яку важко розібрати.

## Hardest seams (test-confidence points — distinct from the contract Seam above)
- **Seam 1: `place_many`** — три задачі: перша стає зайнятістю для другої; вільна t1, що без правила зайняла б слот
  названої t2, стоїть в іншому місці; названий день — лише в той день навіть
  коли раніший день вільний; задача, що не вміщається, — `unplaced`, інші ставляться; одна задача — той самий
  результат, що `place` S3.
- **Seam 2: запис кількох** — фейк Calendar S3: «так» пише кілька подій з різними `event_id`; падіння після
  створення другої (відповідь загублена) → наступне «так» зі старим відбитком показує решту («Записано не повністю —
  ось решта:») і робить нуль створень, друга знайдена кроком 0; «так» з новим відбитком пише лише те, що лишилось;
  варіант: між падінням і повтором у календарі з'являється чужа подія — нова розстановка решти не перетинає
  справжніх подій уже записаних задач; повторне «так» після «записано» — нуль нових.
- **Seam 3: дописування** — друге повідомлення до «питаю тривалість» додає задачу, питання далі за першою без
  тривалості; після «записано» — нова чернетка.

## Invariants (rules that hold for every input in the stated domain)
- **I1** — На будь-яку послідовність «так» до одного плану кожна задача дістає не більше однієї події.
  - Domain: будь-яка кількість задач (1–N), будь-які падіння між створенням і записом, будь-які відбитки.
  - Source: AC6 фічі; S3 I3.
  - Broken by: один `event_id` на план; крок 0 лише для першої задачі; власна записана подія як зайнятість.
- **I2** — Задача без названого часу ніколи не перетинає ні зайнятість, ні жодну іншу розставлену задачу (зокрема з
  названим часом), а задача з названим днем стоїть лише в той день.
  - Domain: будь-які задачі без названого часу (з днем чи без), поруч із будь-якими задачами з названим часом, будь-яка
    зайнятість, перевод літо/зима.
  - Source: G1 («пропонувала там, на коли поставити»); domain-map крок 3.
  - Broken by: розстановка кожної задачі окремо без попередніх; день у UTC замість поясу календаря; повторна
    розстановка вже записаних задач без їхніх справжніх подій у зайнятості; розстановка в `order` без попередньої
    зайнятості від задач з названим часом.
- **I3** — Задача без часу ніколи не дістає події і не дістає питання тривалості.
  - Domain: будь-яка задача з `needs_time=false`, будь-які відповіді.
  - Source: AC3a фічі; domain-map «одна задача живе в одному місці».
  - Broken by: тривалість за замовчуванням для всіх; розстановка всіх задач.

## Exit criterion
- `pytest` зелений: Seam 1–3, `test_I1_…`…`test_I3_…`; запечатані тести S3, S4 F1 зелені без змін; `node --test`
  зелений.
- Smoke зі справжньою моделлю `scripts/smoke_several_tasks.py` (Сонько, без входу Google: справжній Gemini, фейк
  Calendar): 5 фраз з кількома задачами розбираються в задачі з правильними `needs_time`, `constraints.day` і
  тривалістю там, де її названо; результат — у звіті Сонька. S2 F2 починається, коли smoke пройшов.
- Розгортання Соньком; tracer на розгорнутій адресі: фраза з трьома задачами (одна «у понеділок», одна без часу,
  одна з часом) → питання тривалості, якщо треба → один план → «так» → дві події (нотаріус — у понеділок), задача без
  часу показана, не записана; повторне «так» — без нових подій. Виконує власник; до того — «код готовий, чекає
  розгортання», не DONE.
